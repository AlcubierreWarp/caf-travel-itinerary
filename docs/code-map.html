How the CAF Digital Travel Itinerary is built

A static analysis of app/app.html and app/itin.js (version 1.10 beta 9). It lists every top-level function and value and links them wherever one calls or reads another, so you can see the structure Claude has been building and where it has drifted.

What this tells you, and what to ask for

  1. One well-labelled file with no walls between the labels

    The app is 4,319 lines in a single closure, split into 26 named sections in a sensible order. Any function can call any other, and 15 of the 26 sections now depend on each other in one loop: state, derived, rendering, the Standard and Beautify layouts, drafts, device storage and 8 others. A change in any of them can ripple into the rest.

    Ask for: a stated dependency direction (foundation, then state, then derived, then screen and PDF), checked by a test that fails when a lower section calls a higher one.

  2. The claim object S is the real backbone

    95 functions and handlers in 16 sections read or write S directly, next to 24 other mutable top-level variables (R, IMP, CROP, building and so on). This is the main reason the sections are tangled.

    Ask for: only the state section changes S; every other section calls a named function such as setStatus() to change it.

  3. Shared helpers live where they were first needed

    tripDates() and locFor() sit in rendering, yet 20 and 8 functions use them, most of them in the PDF layouts. dDow() and primaryCur() sit in Beautify, yet the Travel Itinerary layout uses them. This is most of what ties the layouts to the screen code.

    Ask for: a "claim facts" section (trip dates, locations, meal counts, currencies) that the screen and every layout read from.

  4. The PDF layouts are 35% of the app and lean on each other

    Standard, Beautify and Travel Itinerary together are 1,530 lines. build(), the Build button for every layout, is filed in the Travel Itinerary section and calls prettify() and prettyDraw() from Beautify, and Beautify holds the layout toggles for all three. As it stands, retiring Beautify would break the Travel Itinerary layout.

    Ask for: a small "package builder" section that owns build() and the layout toggles, with each layout only drawing pages.

  5. Two sections are grab-bags

    drafts holds draft saving plus email and sharing, version labels, notices, pull to refresh and the language switch. language holds T() plus dates, money, ranks, provinces and jurat tables. The labels no longer describe what is inside.

    Ask for: split them into sharing, app shell, and formatting, so the map stays honest.

  6. itin.js is the pattern to copy

    Pure functions, its own file, its own tests, one public object and one caller. It is the only part of the app with a real wall around it.

    Ask for: the same treatment for the calculations in derived (totals and checks) next, since a wrong total is the costliest bug this tool can ship.

  7. Three functions are never called

    meals() and declExpense() in the PDF section and dRange() in Beautify have no callers anywhere in the source.

    Ask for: delete them after a quick check.

How this map was made

A script parsed the source branch with a JavaScript parser, took every top-level function and value inside the app's closure plus itin.js, and linked two of them whenever one names the other. Sections come from the /* ---------- name ---------- */ markers. Top-level code that is not a function (mostly event listeners) is shown as a "wiring" entry for its section. Limits: a local variable that shares a top-level name can add a few false links, and the inlined libraries (pdf-lib, pdf.js) and French strings (fr.js) are left out. Line links open the source branch on GitHub.
